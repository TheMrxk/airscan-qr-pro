# P4 独立客户端选型方案（待开哥拍板，未动工）

> 状态：**方案评审，未写任何客户端代码**。M2 喷泉码已把"单码光学"链路做到体验闭环，
> 但单屏单 QR + jsQR + 摄像头的物理上限就是几 KB/s。要传 MB 级、冲几百 KB/s~MB/s，
> 必须走 P4：**绕开"摄像头看二维码"这一层**。本文给三条路线 + 推荐，供决策。

## 0. 先回答"为什么必须是客户端"

当前网页链路的三个硬天花板（均为实测/库特性，非优化能解）：
1. **jsQR 按 UTF-8 解码**：裸二进制拿不回，必须 Base64 包一层（+27~33% 膨胀）。
2. **摄像头光学解析力**：V25 上下稳妥，V40 难稳扫；反光/手抖/对焦都吃帧率。
3. **jsQR 单线程**：高密度码解一帧 100–300ms，跟不高刷。

P4 用 **屏幕捕获（像素级精确，无镜头模糊/反光）+ 输出原始字节的解码器（zbar）** 同时干掉这三条。

## 1. 三条候选路线

### 路线 A：纯 Web getDisplayMedia + zbar.wasm（最轻，推荐先做）
- 形态：接收端仍是一个网页（可并进现有 PWA/站点），点"屏幕接收"→ `getDisplayMedia`
  共享发送端屏幕（标签页/窗口/整屏）→ 直接读 V40/矩阵码原始字节 → LT 解码 → 流式写盘。
- 解码：`zbar.wasm`（zbar 的 WASM 移植，直接给原始字节，绕开 UTF-8；可裸二进制零膨胀）。
- 发送端：**保持纯网页/standalone 不变**（PC 只负责播码），符合"一发多收、发送端零安装"。
- 优点：无需安装、跨平台、复用现有协议/lt-code/compressor、改动最小、能立刻验证数量级。
- 限制/风险：
  - getDisplayMedia 主要是桌面 Chrome/Edge 支持好；**手机浏览器基本不支持屏录**——
    路线 A 的接收方是"另一台电脑"，不是手机。手机接收仍走现在的摄像头 PWA。
  - 屏录帧率/分辨率受浏览器与被共享内容影响；HTTPS 必需（现有 CF 已满足）。
  - zbar.wasm 体积约几百 KB，要 vendor 本地化（守离线铁律），并验证它对 QR Byte 原始字节的输出。
- 适合：先证明"屏录 + 原始字节"到底能到多少 KB/s，投入小、见效快。

### 路线 B：Tauri 桌面客户端（最终形态，推荐做正式版）
- 形态：Rust 外壳 + 系统 WebView，安装包小（~5–10MB），内存占用低。
- 取帧：系统截屏 API（Windows 用 DXGI/GDI，跨平台用 scrap/cap 类 crate）或直接复用 getDisplayMedia。
- 解码：可直接调 **原生 libzbar**（非 WASM，性能最好），甚至 OpenCV QRCodeDetector。
- 能力：裸二进制零膨胀 + V40 满密度 + 多码矩阵 + 后续彩色码、流式写盘、断点续传都好做。
- 优点：性能/体积/系统集成都最佳；打包单 exe 方便内网分发。
- 限制/成本：需要 Rust 工具链；开哥主力是 JS/Python，学习/维护成本高于纯 Web；
  跨平台编译（尤其 macOS 签名）较麻烦，Windows 单平台则简单。
- 适合：路线 A 验证收益成立后，做对内正式分发的 Windows 客户端（开哥环境是 Windows 银行内网）。

### 路线 C：Electron 桌面客户端
- 形态：Chromium + Node，生态最熟（就是 JS 全栈），getDisplayMedia/Node 原生都能用。
- 优点：开发心智零切换，可直接复用浏览器全部代码 + Node 侧写文件/调 native zbar。
- 限制：安装包大（~80–150MB）、内存占用高；对内网分发是明显缺点（本身就是为了传小文件，
  结果先装个 100MB 的壳，不优雅）。
- 适合：只求快出一个桌面 Demo、不在意体积时。

## 2. 推荐路径

1. **先做路线 A（纯 Web 屏录 + zbar.wasm）**，目标只是"测出数量级"：
   复用 protocol v3 / lt-code / compressor，新增一个"屏幕接收"页和一个取帧/解码适配器
   （协议与介质解耦，本来就是 §3 P4 的设计前提）。先不碰打包。
2. 收益若达标（几百 KB/s 量级、MB 级文件可传），再用 **路线 B（Tauri，Windows 单平台）**
   做正式客户端；若嫌 Rust 成本高，可退而用路线 C Electron 快速落地。
3. 协议侧只做一件事：META/DATA 帧预留的能力位里加 `enc`（0=base64 可打印 / 1=raw 原始字节），
   两端握手选最高效编码；网页摄像头端继续 enc=0，屏录/客户端 enc=1，互不影响、优雅降级。

## 3. 决策点（请开哥选）

- **D1**：先做哪条？建议 **A（纯 Web 屏录验证）**。
  - [ ] A 纯 Web getDisplayMedia + zbar.wasm（推荐）
  - [ ] B 直接上 Tauri 原生客户端
  - [ ] C Electron 客户端
  - [ ] 暂不做 P4，先把 M3 多码矩阵在网页摄像头这条线做到底
- **D2**：接收主力设备到底是谁？
  - [ ] 另一台电脑（屏录路线成立）
  - [ ] 仍是手机（那 P4 屏录不适用，应优先把 M3 矩阵 + Worker/WASM 做透）
- **D3**：目标文件量级？（决定是否值得上客户端）
  - [ ] ≤ 500KB，网页够用
  - [ ] 1–10MB，需要 P4
  - [ ] 几十~几百 MB，P4 + 流式写盘/断点续传是刚需

> 备注：以上收益数字（几百 KB/s~MB/s、V40 稳定等）是工程推断，需在路线 A 的屏录对拍里
> 用真实数据证实/证伪，再决定要不要投入 Tauri。不会在没数据前直接写客户端。
